1. Read and follow the `exptree` skill (`~/.gemini/config/plugins/exptree/skills/exptree/SKILL.md`). It includes exact `exptree` CLI flags — do NOT waste turns reading `exptree` Go source code.
2. **Scientific Readiness Gate (Enter Where You Are — No Premature Coding)**: Do **NOT** blindly scaffold a new repo or fabricate baseline code on Turn 1 when the user is still at an open-ended survey or problem-framing stage. Check 3 readiness preconditions (skip any already settled by the user's request):
   - **(a) Direction**: Are the research question and direction decided? If the user asked to survey papers/solvers and identify topics, finish scouting first and align with the user before branching or coding.
   - **(b) Carrier & Baseline**: Are the target codebase and real `node-0` baseline agreed (e.g. modifying an existing local/remote solver vs. building a new testbench)? Prefer existing code/solvers — NEVER write hundreds of lines of ad-hoc code just to fake a placeholder baseline, and NEVER copy remote SSH codebases into a local shadow repo just to run `scp` loops.
   - **(c) Eval & Runtime**: Are the benchmark set, metrics, and runtime budget clear (synchronous for fast tasks; `-timeout 0` / `-detach` + `exptree step` / `exptree record` for multi-hour cluster/GPU runs)?
   Once concrete experimentation is agreed: for local work, run `exptree init -repo "$REPO" ...`; for remote SSH hosts (`ssh <host>:/path`), automatically run `exptree deploy -ssh <host>`, initialize `exptree` inside the remote solver repo (never `git add` multi-GB benchmark parent directories), and run `exptree bind -ssh <host> -repo <remote-repo>` locally so the ExpTree sidebar attaches with zero manual config.
